# 09 设计决策记录

每条决策记录决定、理由与代价。本文保留当前 Go 分支 D1–D11 的方向，并补充 D12–D16；目标设计不代表功能已实现，现状见 [README](../README.md)，实现顺序见 [路线图](08-roadmap.md)。

## D1 单仓库，两个垂类共用内核
- **决定**：LLM Agent 评测与具身策略评测放在同一仓库，共享 `internal/` 下的调度、存储、统计、归因、报告。
- **理由**：两者评测循环同构（见 01 §2）；共享内核迫使抽象足够干净；统计与归因逻辑只需实现和校准一次。
- **代价**：抽象设计成本更高；需要警惕为了"通用"而牺牲某一垂类的表达力。规则：垂类特有的概念放在各自 Worker / 适配器目录，进入 `internal/core` 前必须证明两个垂类都需要；当前仓库采用 `workers/`，不要求另建 `verticals/`。

## D2 控制面用 Go，环境 Worker 用 Python
- **理由**：调度、存储、并发、服务治理是 Go 的强项；仿真器、VLA 推理生态在 Python。用协议隔离，各用所长。
- **代价**：跨语言的协议维护成本；通过 protobuf 生成代码缓解。

## D3 拉模式调度 + 租约
- **决定**：使用拉模式与有期限的租约。当前 episode_key 去重只保证结果表不重复插入，仍需 D13 的 Attempt、fencing 和持久化待提交队列。
- **理由**：Worker 能力异构，拉模式便于分配适合的任务与控制资源；允许故障后重复执行，但每个计划位置按规则只选择一次结果。不承诺端到端 exactly-once。
- **代价**：租约过期到重新调度之间存在延迟；对评测场景（分钟级 episode）可接受。

## D4 被测对象服务化
- **理由**：隔离依赖（不同策略需要不同版本的深度学习框架），通过统一协议支持批量推理并减少环境与策略适配组合。Describe 必须声明协议、状态和动作能力；Reset / Act 的超时不等于服务端未执行，不能默认安全重试。
- **代价**：多一次进程间通信；对具身场景，同机部署时开销可忽略。

## D5 infra_error 与 unknown 不计入主成功率分母，但必须可见
- **决定**：主成功率为 S/(S+F)，infra_error 与 unknown 分列，保留 10 §13 已确认的口径；完成度与目标有效性阈值见 07 §1。
- **理由**：基础设施故障不是模型能力，证据不足也不能直接判失败；但忽略这些位置可能形成选择偏差，须同时展示完整计划与缺失情况。
- **代价**：需要定义清晰的 error_kind 边界（见 04 §2.4：模型输出格式错误是失败，不是 infra_error）。

## D6 用 Wilson 区间和配对检验，而不是只报点估计
- **理由**：评测的目的是做决策；没有不确定性的数字无法支持决策。Wilson 适用于相应独立二元采样；相关重复、来源成组、加权和配对比较按各自假设选用方法，不机械套用单一区间。
- **代价**：报告更复杂；需要样本量规划，评测成本可能上升。

## D7 自建内核，集成现有环境
- **理由**：内核是评测平台的核心价值；环境与 benchmark 必须和社区实现一致才能与公开结果对齐。
- **代价**：要跟随上游环境的版本变化；通过 manifest 锁定版本缓解。

## D8 具身首期只做 MuJoCo 系（LIBERO）
- **理由**：任务、仿真接口和公开 checkpoint 便于建立可核验基线。实际 CPU / GPU、渲染与驱动要求按锁定版本验证；标定须对齐任务、初态、动作与模型，不能仅凭置信区间重叠认定复现成功。
- **代价**：首期不覆盖 Isaac 系高保真场景与真机。

## D9 Judge 视为需要校准的仪器
- **理由**：未经校准的 LLM Judge 会系统性偏差，且偏差方向未知。
- **代价**：需要维护人工标注集。

## D10 评测集格式由 Detroit 定义，生产方直接产出
- **决定**：评测集格式协议（10）放在 Detroit 仓库维护。CasePick 等数据生产方直接产出该格式，公开 benchmark 由 loader 转换成该格式。
- **理由**：消费方决定自己能接受什么，最不容易出现两边各改各的；一份格式同时覆盖插件产出、用户自建评测集和公开 benchmark，内核只需要一个导入入口。
- **代价**：生产方的私有信息只能放进 `extensions`；协议改动要同时考虑多个生产方。

## D11 评分定义可以和题目分开分发
- **决定**：题目（`detroit.case/v2`）和评分（`detroit.scoring/v2`）各有摘要和修订号；评分通过 `target.task_digest` 绑定到题目的具体内容，一道题可以挂多份评分。题目里也可以内联一份默认评分。
- **理由**：rubric 和检查比题目改得频繁；分开后改评分不会让题目变成新题，可以对已有制品重评分而不重跑被测对象；同一道题可以对比不同评分标准（如严格版和宽松版）。
- **代价**：要维护"评分 → 题目"的引用，题目的 `task` 变化后旧评分会失效，需要人确认后迁移。


## D12 冻结解析后的执行计划，区分提交与实验身份

- **决定**：冻结任务、初态、材料、Subject、环境、预算、loader、采样和重试政策；Worker 按摘要取包。spec_digest / plan_digest 表示内容，run_id 表示实验实例，submission_key 表示幂等提交；显式区分继续与新建。
- **理由**：当前 RunID 仅由 RunSpec 推导，taskset_hash 只进入 manifest，Worker 又会加载来源；同名任务变化可能被误当作旧实验。评分变化只产生 Evaluation，Variant 保持“受控扰动”含义。
- **代价**：需要冻结存储、漂移检测和旧 ID 迁移；历史记录没有的快照不得补造。

## D13 Attempt fencing 与持久化上报

- **决定**：每次执行有 attempt_id、lease_epoch 和 Worker incarnation；Heartbeat / Report 校验当前所有权。执行后先写持久化 outbox，reporting 保活直到 ACK 或明确失效；失效上报保留审计与成本，不覆盖选定结果。
- **理由**：当前 Worker 在 Report ACK 前停止续租，且首个到达结果胜出；断网和僵尸 Worker 可能丢失已完成结果或提交旧结果。租约只约束所有权，不能立即阻止远端执行。
- **代价**：增加状态、恢复对账、有限补交窗口和队列背压。取消、上报与重派竞争须事务化；结果幂等不意味着任务只执行一次。

## D14 执行、评分、报告独立版本化

- **决定**：ExecutionResult 保存轨迹与制品，Evaluation 绑定任务、评分规格、证据和评分器版本，ReportSpec 固定选择与聚合。scorers.select: all 展开多份评分，不重复执行、不增加统计样本。跨语言 v2 摘要按 10 §4 的正向投影与 JCS 计算。
- **理由**：D11 的独立分发只有在存储和执行层同样解耦时，才支持可追踪重评与不同评分标准比较。
- **代价**：需要额外表、版本与缓存策略；未持久化的在线终态可能无法重评，随机 Judge 重评需独立身份与用量。

## D15 制品完整度与资源生命周期进入执行契约

- **决定**：保存原始字节、权限、格式、摘要与采集错误，原子提交 ArtifactManifest；必要评分证据缺失显式传播。Destroy 确认成功后才标完成，失败进入可重试清理；整个 episode 有独立监督与资源约束。
- **理由**：事后磁盘检查不是硬配额，截断文本不是完整文件，销毁请求发出不代表容器已回收。
- **代价**：增加制品存储、配额后端与残留资源对账；远程 Worker 需要共享可访问的制品引用。

## D16 保留条件成功率，补齐有效性与推断前提

- **决定**：继续 D5 与 10 §13 的口径；每次报告显示固定计划、完成度和各类缺失，执行事先冻结的有效性门槛。N=0 显式未定义；按独立、配对、分组或加权结构选择方法。缺失敏感性范围作为补充，不替代主指标。
- **理由**：既保留已确认的产品语义，也防止失败样本被选择性丢弃后夸大能力；多份评分和重试都不能膨胀样本。
- **代价**：报告需区分实验执行状态、有效性和统计适用性；基线与回归检查需要额外的完整性约束。费用记录所有实际尝试，而非只记录选中结果。
