# 09 设计决策记录

每条决策：背景 → 决定 → 理由 → 代价。

## D1 单仓库，两个垂类共用内核
- **决定**：LLM Agent 评测与具身策略评测放在同一仓库，共享 `internal/` 下的调度、存储、统计、归因、报告。
- **理由**：两者评测循环同构（见 01 §2）；共享内核迫使抽象足够干净；统计与归因逻辑只需实现和校准一次。
- **代价**：抽象设计成本更高；需要警惕为了"通用"而牺牲某一垂类的表达力。规则：垂类特有的概念放在 `verticals/`，进入 `internal/core` 前必须证明两个垂类都需要。

## D2 控制面用 Go，环境 Worker 用 Python
- **理由**：调度、存储、并发、服务治理是 Go 的强项；仿真器、VLA 推理生态在 Python。用协议隔离，各用所长。
- **代价**：跨语言的协议维护成本；通过 protobuf 生成代码缓解。

## D3 拉模式调度 + 租约
- **理由**：Worker 能力异构；拉模式天然负载均衡；租约 + 幂等键使任何组件崩溃都不会丢失或重复计数结果。
- **代价**：租约过期到重新调度之间存在延迟；对评测场景（分钟级 episode）可接受。

## D4 被测对象服务化
- **理由**：隔离依赖（不同策略需要不同版本的深度学习框架）；支持批量推理；与业界主流做法一致；N+M 而非 N×M 的集成成本。
- **代价**：多一次进程间通信；对具身场景，同机部署时开销可忽略。

## D5 infra_error 不计入分母，但必须可见
- **理由**：基础设施故障不是模型能力；但如果隐藏它，可能掩盖"模型在某类任务上导致环境崩溃"的问题。
- **代价**：需要定义清晰的 error_kind 边界（见 04 §2.4：模型输出格式错误是失败，不是 infra_error）。

## D6 用 Wilson 区间和配对检验，而不是只报点估计
- **理由**：评测的目的是做决策；没有不确定性的数字无法支持决策。
- **代价**：报告更复杂；需要样本量规划，评测成本可能上升。

## D7 自建内核，集成现有环境
- **理由**：内核是评测平台的核心价值；环境与 benchmark 必须和社区实现一致才能与公开结果对齐。
- **代价**：要跟随上游环境的版本变化；通过 manifest 锁定版本缓解。

## D8 具身首期只做 MuJoCo 系（LIBERO）
- **理由**：不依赖 RTX 显卡；有公开 checkpoint 与公开分数可标定；社区封装成熟。
- **代价**：首期不覆盖 Isaac 系高保真场景与真机。

## D9 Judge 视为需要校准的仪器
- **理由**：未经校准的 LLM Judge 会系统性偏差，且偏差方向未知。
- **代价**：需要维护人工标注集。

## D10 评测集格式由 Detroit 定义，生产方直接产出
- **决定**：评测集格式协议（10）放在 Detroit 仓库维护。CasePick 等数据生产方直接产出该格式，公开 benchmark 由 loader 转换成该格式。
- **理由**：消费方决定自己能接受什么，最不容易出现两边各改各的；一份格式同时覆盖插件产出、用户自建评测集和公开 benchmark，内核只需要一个导入入口。
- **代价**：生产方的私有信息只能放进 `extensions`；协议改动要同时考虑多个生产方。

## D11 评分定义可以和题目分开分发
- **决定**：题目（`detroit.case/v2`）和评分（`detroit.scoring/v2`）各有摘要和修订号；评分通过 `target.task_digest` 绑定到题目的具体内容，一道题可以挂多份评分。题目里也可以内联一份默认评分。
- **理由**：rubric 和检查比题目改得频繁；分开后改评分不会让题目变成新题，可以对已有制品重评分而不重跑被测对象；同一道题可以对比不同评分标准（如严格版和宽松版）。
- **代价**：要维护"评分 → 题目"的引用，题目的 `task` 变化后旧评分会失效，需要人确认后迁移。
