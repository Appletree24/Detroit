# Detroit：Harness 开发与 LLM 评测面试指南

> 当前已有 M1 基础实现与确定性测试；真实容器与模型实验尚待完成。下面的经历模板只能在对应实现与实验完成后使用，当前证据见 [M1.md](M1.md)。
> 以 [DESIGN.md](../DESIGN.md) 为准。目标岗位：Agent Harness 开发 / LLM 评测工程。

## 1. 一个项目，两条深入路径

业务动机是为自己选择 coding agent，并验证策略修改是否有效。完整产品提供任务运行、独立评分、轨迹诊断与对比报告；自己的参考 Harness 使上下文与工具策略成为可控制、可修改的实验对象。

| 岗位 | 重点证明 | 连续追问链 |
| --- | --- | --- |
| Harness 开发 | 能实现并理解模型与环境之间的执行机制 | 输入构建 → 压缩与回读 → 工具状态 → 恢复/停止 → 实际效果 |
| LLM 评测 | 能定义能力、构造可信测量并解释实验结果 | 能力定义 → 数据/验证器 → judge 效度 → 控制变量 → 统计/归因 |
| 两者共享 | 能把问题研究转成可用产品 | 真实失败 → 机制假设 → 策略实现 → 受控实验 → 保留任务验证 |

选择一个实测充分的案例深入，其余模块用于解释完整闭环。运行隔离、取消和证据持久化保证实验可信，不占据主要面试叙述。

## 2. 三种讲述长度

### 30 秒：项目与主线

完成 M1–M3 后可用：

> 我做了一个用于改进和比较 coding agent 的实验平台。自己实现了轻量 Harness，重点处理长任务的上下文压缩、证据回读和工具恢复，同时接入 Pi/OMP 做外部对照。平台用独立测试验证结果，保存每轮实际输入和工具轨迹，再通过受控实验比较质量、成本与耗时。核心案例是检验结构化压缩能否减少长任务中的信息遗漏。

主投评测岗且完成 M4 后，将中间部分改为任务分组与去重、验证器有效性、judge 校准和配对统计。已实现策略不等于已证明收益；没有稳定提升时如实描述结论。

### 3 分钟：围绕一个真实问题

1. **动机**：日常选择 agent 时，仅看最终回答和一次成功截图无法判断稳定性与成本。
2. **问题**：展示一条真实失败；任务要求、缺失证据、错误修改和验证断言形成关联。
3. **机制**：解释原始历史、可变工作摘要与本轮模型输入如何分离，以及来源、失效和回读策略。
4. **测量**：固定模型、工具和预算，与滑动窗口比较；按任务配对，并在保留任务上验证。
5. **结论**：给出完整样本、质量/成本差值和区间，说明哪些任务有效、哪里无效，以及下一步假设。

### 10 分钟：按岗位深入同一实验

Harness 岗先打开 ContextBuilder 与一轮真实请求，讲预算、工具配对和摘要过期；再演示一个含副作用的错误为什么不能自动重试，最后说明行为收益如何验证。

测评岗先解释“信息保持”如何落到可验证 Case，讲独立测试、数据划分、人工参考标签与误差来源；再讲随机性、配对单位、缺失和成本口径，最后用消融支持有限的机制结论。

技术栈只需交代 TS/Bun、SQLite、Docker。复用 SDK 做模型请求，自己实现 agent loop；外部 Pi/OMP 的机制明确归于各自项目。

## 3. 三个核心案例与证据

### 案例 A：压缩后遗漏了早期读取的兼容性信息

使用缓存库修复等任务：早期工具输出揭示关键行为，经历长日志和跨文件修改后，最终代码违反兼容性测试。

应展示：

- 原始输出、本轮 ContextView、压缩 manifest 和最终失败断言。
- Structured 与 Sliding 的完整对照，显式指令保留政策、模型/工具/预算一致。
- 来源引用、文件版本检查和按需回读对应的实现与性质测试。
- 全部重复、保留任务结果，以及无回读或无失效检查的单项消融。

必须能解释：固定用户提示不能阻止历史工具证据丢失；来源可核验不代表摘要语义无误；摘要模型额外调用计入成本。单条时间线支持关联，受控对照才支持有限的机制贡献判断。

### 案例 B：命令已经产生副作用，但没有返回结果

可重置 fixture 中，命令完成文件写入后模拟结果回报丢失。Harness 应将结果记为 unknown，先检查状态，无法判断时停止或显式恢复。

应展示：

- 错误分类、所属重试层、副作用类别和恢复决策。
- 只读工具可并行、读写混合默认顺序执行的场景。
- 结果去重与外部副作用的不同边界，取消和进程组回收记录。
- 最终文件/副作用次数，而非只看 agent 的成功声明。

必须能解释：同一个 call ID 不意味着外部 exactly once；恢复成功率需要报告故障暴露条件；脚本化模型验证逻辑，真实模型实验验证策略效果。M5 扩展此案例时再增加系统性效果实验。

### 案例 C：评分器认为更好，但独立验证不支持

给 judge 一组来源隐藏、长度不同、部分测试失败的候选产物，交换 A/B 顺序，与人工参考标签对照。

应展示：

- rubric、原始 judge 输出、人工分歧、校准集和保留集身份。
- 一致性、位置/长度/同源偏差、弃权率与具体错判。
- 确定性结果和主观维度分别呈现，不以高主观分覆盖测试失败。
- 同一不可变产物用两版评分器重评分，以及新增评分费用。

必须能解释：人工参考也有噪声；自报置信度需要校准；不同 judge 相互一致不能证明正确；评分器在其校准范围之外的结论要保留限制。

## 4. 高频追问与所需材料

| 追问 | 回答核心 | 材料 |
| --- | --- | --- |
| 你到底自研了什么？ | 模型 loop、上下文、工具与恢复策略；SDK/容器属于复用 | 单次任务调用链与依赖边界 |
| 为什么还接 Pi/OMP？ | 外部对照与日常选型；自研 Harness 提供可控消融 | 机制实验与产品比较各一份规格 |
| 为什么不用 Harbor/Inspect？ | 现成评测生态可复用；项目聚焦可控机制与实证闭环 | 选型 ADR、兼容范围和维护代价 |
| 为什么用 TS/Bun？ | SDK 生态和统一迭代；语言不替代机制深度 | 固定版本 smoke test 与实际实现 |
| 怎么分配 context budget？ | 工具 schema、指令、输出预留、估算误差与溢出恢复 | 一次构建 manifest 与超限测试 |
| 摘要为什么可信？ | 来源/新鲜度可检查，语义保真靠验证，允许未知和回读 | 文件更新 Case、语义错误样例 |
| 工具结果被截断怎么办？ | 有界预览与真正可用的回读入口；原文生命周期 | 大输出 Case 与 read-artifact 调用 |
| 用户改主意怎么办？ | 最新有效约束和 supersedes；旧要求仍保留为历史 | 同一任务内的纠正测试 |
| 哪些工具可并行？ | 无依赖只读；写串行、读写顺序，shell 默认有副作用 | 并发场景的文件状态与墙钟时间 |
| 为什么不重试所有错误？ | 参数错误、临时错误和副作用未知需要不同决策 | 写成功但回报丢失的测试 |
| 怎么区分模型和 Harness 的影响？ | 固定一方比较另一方；交叉实验看交互效应 | 冻结规格及结果矩阵 |
| 自建任务测到了什么？ | 能力到 Case 到断言；合成任务与真实仓库迁移 | 任务卡、标签、已知正反解 |
| 如何防止数据泄漏？ | 家族/仓库分组、近重复、测试集使用记录；承认预训练未知 | split manifest 与数据来源 |
| 验证器本身可能错吗？ | 正确/错误解、变异、flaky 检查；故障与任务失败分离 | verifier 验证集与错判修复 |
| Judge 凭什么可信？ | 人工参考、独立保留集、偏差与弃权；主观维度单列 | 校准报告与原始标签 |
| 20 道题跑 5 次是 100 个独立样本吗？ | 重复属于任务内观测；任务/家族聚类，结论受独立组数限制 | 配对汇总代码和原始 Trial |
| 质量没降、费用降了，怎么证明？ | 同时报告差值区间；“没降”需预设容忍度，未知费用不能当零 | 质量/费用口径与完整分项 |
| 重试、超时和未完成怎么算？ | Trial/Attempt 分离，预设政策，覆盖率和失败分母透明 | 一个含失败与重试的批次 |
| 轨迹能证明根因吗？ | 观测关联、对照、消融逐层增强证据；不声称内部因果真相 | 失败片段与对应实验 |
| 能从某一步重放吗？ | 浏览和重评分已有证据；续跑需要恢复环境和状态并重新调用 | 当前支持范围或分叉实现 |

## 5. 项目证据包与简历模板

每个核心主张对应四类材料：实现代码、确定性测试、冻结实验规格、真实结果及限制。优先保留一条可完整追问的证据链。

| 材料 | 最低要求 |
| --- | --- |
| 核心机制 | 可定位到 context/runtime/tool 模块，说明自己的贡献与复用部分 |
| 任务与评分 | 任务来源、能力标签、split、验证器检查和人工参考说明 |
| 实验规格 | 代码/模型/镜像版本、全部配置、预算、重复、统计单位与重试政策 |
| 结果 | 全部 Trial、缺失与失败、差值区间、辅助调用成本、适用范围 |
| 产品演示 | 从总体报告进入一个失败，再进入本轮实际输入和机制实现 |
| 开源交付 | 快速开始、无凭据示例、许可、复现实验说明与贡献边界 |

以下模板只选已完成的 2–3 条；方括号需填写可复核数据。未公开发布前不写“开源”，没有显著收益时也不必强行补提升数字。

> **Detroit｜Coding Agent Harness 与评测平台｜TypeScript / Bun / SQLite / Docker**

- 实现可控 Coding Agent Harness，构建模型调用、工具执行、恢复与停止循环；通过原始历史、工作摘要和模型输入分离，实现带来源追踪、文件失效检查和按需回读的上下文压缩。
- 建立覆盖 [任务数/独立家族数] 的能力任务与独立验证器，固定模型和预算比较 [策略]，采用任务/家族配对统计与消融，报告 [具体质量与成本结果、区间及适用范围]。
- 接入 Pi/OMP，统一实验配置、隔离运行和版本化证据，提供质量、成本、代码 diff 与上下文轨迹报告，支持定位失败并重新验证策略修改。
- 建立 [样本量、标注方式] 的人工参考集，完成 judge 的 [具体维度] 校准，检查位置/长度偏差、弃权与一致性，并在独立保留集报告 [实测结果]。

Harness 岗优先前两条，第三条说明完整产品；测评岗优先第二、第四条，再以第一或第三条证明执行落地。M2 前不写正式机制收益，M3 前不写完成两种外部接入，M4 前不写已建立 judge 校准体系。

模型权重未变时，准确描述“特定任务上的 agent 表现变化”；若实际改变的是 Harness，不笼统称为基础模型能力提升。数据量很小时，研究方法、失败分析和结论边界比夸大排名更有说服力。

## 6. 五分钟现场演示

1. **产品入口**：打开一份真实静态报告，交代任务、配置、预算和总体质量/成本。
2. **失败证据**：进入一个失败任务，展示独立断言、代码 diff 与相关工具输出。
3. **机制定位**：比较该轮输入与原始历史，解释缺失或过期信息，打开对应 context 策略。
4. **实验验证**：展示预设变体、完整重复、消融与保留任务结果，说明观察是否支持假设。
5. **实现落地**：运行一个确定性的上下文或工具恢复测试，结束于对应实现及保证边界。

现场不依赖临时付费模型调用。已有真实报告与 scripted model 测试明确区分；若发现负结果，说明机制在哪些任务无效。演示必须贯穿“任务→执行→评分→诊断→再实验”，让两个岗位都能看到一个完整产品。
