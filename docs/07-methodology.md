# 07 评测方法论

本文是 Detroit 中所有"数字"背后的规则。

## 1. 结果的有效性

一次 run 的结果有效，当且仅当：

- `infra_error` 比例 ≤ 5%（可配置）；超过则整次 run 标记为 `invalid`，报告只展示诊断信息。
- `unknown`（评分依据不足）比例 ≤ 10%（可配置）；超过同样标记为 `invalid`。`unknown` 不计入成功率的分母，也不算失败。
- 标定 suite（如有）通过：复现值落在公开值的置信区间内。
- manifest 完整（见 §5）。

## 2. 统计

### 2.1 单个成功率：Wilson 区间
n 次试验、成功率 p̂、z = 1.96：

```
center = (p̂ + z²/2n) / (1 + z²/n)
half   = z / (1 + z²/n) · sqrt( p̂(1−p̂)/n + z²/4n² )
CI     = [center − half, center + half]
```

选 Wilson 而不是正态近似的原因：成功率接近 0 或 1、样本量小时，正态近似区间会越界或过窄，而这正是评测中最常见的情形。

直观量级（p≈0.5）：n=10 时半宽约 ±0.3；n=100 时约 ±0.1。**这意味着"每任务 10 个 episode"得到的单任务成功率几乎没有区分度**，单任务结论必须谨慎，结论应在 suite 层面给出。

### 2.2 两个模型比较：配对检验
当两个模型在**相同的 (task, variant, init_state, seed)** 上评测时，结果天然配对。使用 McNemar 检验，只看不一致对：

```
b = A 成功且 B 失败 的 episode 数
c = A 失败且 B 成功 的 episode 数
χ² = (|b − c| − 1)² / (b + c)       # b + c 较小时改用精确二项检验
```

配对设计比独立两样本检验更省样本，因为它消除了"任务难度"带来的方差。这也是 Detroit 坚持固定初始状态与 seed 的原因之一。

### 2.3 多次重复：pass@k 与 pass^k
对同一任务重复 n 次、成功 c 次：

- **pass@k**（k 次里至少一次成功）的无偏估计：`1 − C(n−c, k) / C(n, k)`。适合衡量"能力上限"。
- **pass^k**（k 次全部成功）的估计：`C(c, k) / C(n, k)`。适合衡量**可靠性**，对生产环境 Agent 更有意义。

Agent 对话类任务默认同时报告 pass^1 与 pass^k（k=3 或更大）。

### 2.4 样本量规划
检测两个成功率之差 δ，显著性 α=0.05、功效 0.8，每组所需样本约：

```
n ≈ (1.96 + 0.84)² · [p₁(1−p₁) + p₂(1−p₂)] / δ²
```

p≈0.5、δ=0.1 时每组约 390 个 episode。`detroit plan --delta 0.1 --baseline 0.5` 在提交前输出这一估计，避免跑完才发现样本不够。

### 2.5 多重比较
同时比较多个扰动轴 / 多个 suite 时，对 p 值做 Holm-Bonferroni 校正，报告中同时给出原始与校正后的结论。

## 3. Judge 校准

LLM / VLM Judge 本身是被测量的仪器，必须校准：

1. **人工标注集**：每个垂类维护一个 ≥100 条的人工标注失败样本集。
2. **一致性指标**：Judge 与人工的 Cohen's κ；按标签输出混淆矩阵。κ < 0.6 的标签在报告中标注"低可信"。
3. **偏差检查**：
   - 位置偏差（成对比较时交换顺序，结论应不变）；
   - 冗长偏差（Agent 回复长度与 Judge 打分的相关性）；
   - 自我偏好（Judge 与被测模型同源时单独报告）。
4. **版本化**：Judge 的模型、提示词、解析逻辑共同决定 `scorer.Version()`；不同版本的标签不混合统计。

## 4. 失败归因

### 4.1 打标
见 05 §6、06 §6。每个失败 episode 可有多个标签，但有一个 `primary` 标签用于统计。

### 4.2 聚类（发现 taxonomy 之外的新失败模式）
对 Judge 给出的 `rationale` 文本做向量化 + 聚类，人工查看大簇的代表样本。若某簇不属于任何已有标签，则提议新增标签并更新 taxonomy 版本。

### 4.3 影响排序
报告中失败类型按"如果这类失败全部修复，成功率能提高多少"排序：

```
impact(label) = count(primary == label) / N
```

并与基线 run 对比，标出"增量最大的失败类型"——这通常就是本次改动引入的问题。

## 5. 可复现性

### 5.1 Manifest
每次 run 生成 `manifest.json`：

```json
{
  "detroit_version": "git:abc123",
  "subject": {"adapter": "openpi", "digest": "...", "params": {...}},
  "env": {"worker_image": "sha256:...", "benchmark": "libero", "benchmark_version": "..."},
  "taskset_hash": "...",
  "seeds": "...",
  "scorers": [{"name": "vlm_failure_judge", "version": "v1", "model": "..."}],
  "hardware": {"gpu": "...", "driver": "..."},
  "spec_hash": "..."
}
```

`detroit run replay <run-id>` 根据 manifest 重新提交一个配置相同的 run。

### 5.2 已知的非确定性来源
- GPU 推理的浮点非确定性（批大小变化也会影响结果）；
- 模拟用户 / LLM 采样温度；
- 工具的 live 模式。

对每个来源，在 manifest 中记录其状态，并在报告中给出"同配置重跑两次的结果差异"（rerun spread），作为噪声基线。

### 5.3 Sanity checks（每次 run 前自动执行）
| 检查 | 目的 |
|---|---|
| 观测朝向检查 | 渲染一帧标定场景，检查图像是否被意外翻转/旋转（社区数据集曾出现图像与仿真场景水平镜像的问题，会悄悄压低分数） |
| 零动作基线 | 被测对象输出全零动作时成功率应接近 0，否则说明成功判定有误 |
| 脚本策略上界 | 对有脚本解的任务，脚本策略成功率应接近 1，否则说明环境或判定有误 |
| 观测 schema 匹配 | Subject 的 `obs_schema` 与 Worker 产出一致 |

## 6. 报告规范

每份报告必须包含：

1. 结论摘要（一句话 + 是否显著）。
2. 有效性检查结果（infra_error 比例、unknown 比例、sanity checks、标定）。
3. 分组成功率表（含 CI、N）。
4. 与基线的配对比较（如有）。
5. 失败分布与影响排序，附代表性样本链接（视频 / 对话）。
6. 吞吐与成本。
7. 输入完整度：按题目的 `task.tools.source` 和 `task.system.status`（10 §6.2）分组展示成功率，标出工具定义或系统提示是近似、缺失的题目。
8. Manifest 摘要。

报告中**不允许出现没有 N 和 CI 的成功率**。
